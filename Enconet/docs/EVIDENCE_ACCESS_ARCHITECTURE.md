# Evidence Access architecture

## Purpose and current boundary

Evidence Access connects each evaluation reference to the exact database-backed evidence that
supports it. The approved implementation is a generated, static, offline review package.
A web service is not required. The retired live GUI is not part of this architecture, and the generated
HTML must not make network requests.

## Data flow

```text
registered raw sources + provenance
              |
              v
SQLite chunks, crumbs, quotes, evaluations, findings, gaps, actions
              |
              v  evidence_resolver.py (read-only, fail closed)
typed evidence_bundle.json
              |
      +-------+-------------------+
      |                           |
      v                           v
evaluation_report.md       evidence_explorer.html
      |                           |
      +----------- deep links ----+
                  |
                  v
review_catalog.json -> review_workspace.html -> package_manifest.json
```

The database is the evidence source of truth. Generated JSON/Markdown/HTML are projections for
review, not places to repair source facts. Stable run, document, criterion, crumb, quote, and chunk
identifiers preserve the path back to source evidence.

## Component responsibilities

| Component | Responsibility | Must not do |
| --- | --- | --- |
| `evidence_resolver.py` | Read exact active graph from SQLite and package | Mutate DB or guess missing links |
| `generate_evidence_bundle.py` | Serialize typed deterministic projection | Publish partial/unresolved evidence |
| `generate_report.py` | Render individual evidence deep links | Embed repository-absolute paths |
| `generate_dashboard.py` | Render self-contained browser UI and escaped JSON | Execute source text as markup/script |
| `generate_review_catalog.py` | Register validated runs only | Discover arbitrary files as trusted runs |
| `generate_review_workspace.py` | Render run-selection landing page | Mix artifacts across runs |
| `build_review_package.py` | Assemble, hash, and validate portable package | Write into a non-empty destination |
| validators/browser harness | Enforce schemas, lineage, links, budgets, behavior | Repair evidence or self-approve gates |

## Artifact model

The inner run quartet—bundle, evaluation package, report, and viewer—must share one run identity.
The catalog adds status and exact hashes. The workspace renders only the catalog. The outer package
manifest inventories all six payload files in deterministic path order. The manifest itself is
pinned by the EA6.1 candidate contract.

Two kinds of hashes have different jobs:

- Source and lineage hashes prove which database/package/manifest/source material produced the
  evidence projection.
- Artifact hashes prove exact generated bytes and prevent mixing or silent modification.

Timing measurements are deliberately excluded from immutable identity because host performance
varies. Approved ceilings remain versioned in `schemas/evidence_access_budgets.yml`.

## Trust boundaries

1. **Raw intake:** only registered, checksum-matched, read-only raw sources may enter the pipeline.
2. **SQLite read boundary:** evidence resolution opens the database read-only/query-only and fails
   on missing, inactive, ambiguous, cross-document, or hash-inconsistent links.
3. **Rendering boundary:** all source-controlled text is data. HTML embedding escapes closing-script,
   C1, bidi, and isolate hazards; DOM insertion uses text-safe rendering.
4. **Path boundary:** catalogs, contracts, and manifests accept contained relative paths only.
5. **Browser boundary:** the package runs locally, makes zero external requests, and exposes no
   write-back API.
6. **Human boundary:** automation proves integrity and interaction mechanics; only the Owner can
   approve usability or promotion, and independent review is a separate gate.

## Determinism and failure behavior

Ordering policies, canonical JSON serialization, explicit UTC generation time, stable identifiers,
and SHA-256 inventories make identical inputs reproducible. Generation writes only candidate paths.
Filtering and evidence resolution fail closed. A missing link, invalid schema, unsafe path, hash
drift, oversized projection, browser error, or external request blocks release.

The browser UI is intentionally disposable: rebuild it from the evidence bundle rather than editing
generated HTML. The bundle is also derived; correct the controlled database/source lineage and
regenerate through the pipeline.

## Extension points

Safe extensions preserve existing boundaries:

- Add a new entity type by updating the canonical schema, resolver, bundle validator, renderer,
  fragment router, citation renderer, fixtures, and browser tests together.
- Add a new run by registering its exact artifact quartet and hashes in `review_packages.yml`, then
  regenerate catalog, workspace, and portable package.
- Add search/filter facets against the embedded typed bundle without network access or DB writes.
- Add export formats through deterministic renderers consuming the bundle, with their files and
  hashes added to the manifest schema.
- Add a live service only after a new Owner decision and superseding architecture decision; it is a
  separate security, lifecycle, concurrency, authentication, and deployment problem.

Do not extend by querying raw files from browser JavaScript, embedding unrestricted HTML, weakening
path/hash checks, hand-editing generated artifacts, or adding an implicit server dependency.
